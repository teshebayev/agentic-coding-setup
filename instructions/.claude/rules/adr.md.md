# Инструкция агенту: `.claude/rules/adr.md`

- **Что это:** когда и как писать ADR (долгоживущее архитектурное решение)
- **Когда подхватывается:** только когда Claude читает или правит файлы из `paths:` (`docs/adr/**`); иначе правило не занимает контекст
- **Действие при переносе:** **подстроить** — каркас общий, поменять команды, пути и примеры под проект

## Что в файле сейчас (проект «DWH-аналитик»)

ADR — только если решение трудно отменить, удивляет без контекста и было компромиссом между реальными
альтернативами. Файл `docs/adr/NNNN-kebab-case.md`, формат из `domain-modeling/ADR-FORMAT.md`, но по-русски:
фронтматтер `status`, заголовок, 1–3 предложения. «Рассмотренные варианты» и «Последствия» — по пользе. Принятый
ADR не переписывается. Кандидаты из сделанного: event log как источник истины, DWH только через MCP, ручные миграции.

## Что должно быть в вашем проекте

То же; язык — ваш; последняя строка — 2–4 кандидата в ADR из уже принятых решений вашего проекта.

## Шаги адаптации

1. Спроси пользователя (или найди в README/архитектурных доках) 2–4 решения, о которых новички спрашивают
   «почему так?» — подставь в строку «Кандидаты».
2. Если артефакты на английском — убери «но по-русски».
3. Держи ADR в `docs/adr/` — этот путь ожидает скилл `domain-modeling`. Если у проекта ADR уже живут в
   другом месте, поменяй `paths:` и текст правила и предупреди пользователя, что скилл будет искать `docs/adr/`.

## Связи с другими файлами

`docs/adr/`, скилл `domain-modeling` (`ADR-FORMAT.md`), `process-invariants.md`, `design-decisions.md`.
