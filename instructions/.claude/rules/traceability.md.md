# Инструкция агенту: `.claude/rules/traceability.md`

- **Что это:** правило трассируемости: у каждого требования ID, каждый артефакт ссылается на ID
- **Когда подхватывается:** всегда, в каждой сессии: у правила нет `paths:` во фронтматтере, Claude Code грузит его как часть CLAUDE.md
- **Действие при переносе:** **подстроить** — каркас общий, поменять команды, пути и примеры под проект

## Что в файле сейчас (проект «DWH-аналитик»)

- Схема ID: `G` цели, `NG` не-цели, `FR` функциональные, `NFR-S` безопасность, `NFR-RP` совместимость replay,
  `NFR-C` стоимость, `NFR-P` производительность, `M` метрики, `Q` открытые вопросы. ID уникальны внутри изменения.
- Таблица «артефакт → как ссылаться»: спека (`# реализует FRn из <change>`), задача (`(FR2, NFR-S1)`), код
  (docstring «Реализует FR2 из <change>.»), тест (комментарий `# FR2: …`), плейбук (`tests.yml`), design.md.
- Не размечать задним числом нетронутый код.
- Проверка перед архивом: `grep -rn "FR2" harness dwh-analyst-mcp tests dwh-knowledge`.

## Что должно быть в вашем проекте

Та же схема, но со своими категориями NFR (например `NFR-S` безопасность, `NFR-P` производительность,
`NFR-A` доступность UI, `NFR-I` i18n, `NFR-C` совместимость API) и строками таблицы под ваши артефакты
(`describe`/`it` в JS-тестах, JSDoc, Go-комментарии…). Команда проверки — grep по вашим каталогам.

## Шаги адаптации

1. Согласуй с пользователем список NFR-категорий — 3–5 штук, которые реально встречаются в изменениях.
2. Замени `NFR-RP`/`NFR-C` и их описания; ту же правку внеси в `openspec/config.yaml` (rules.proposal) и
   `.claude/rules/proposal-format.md`.
3. Замени строку «Плейбук» на свой тип артефакта или удали; поправь синтаксис комментариев под язык.
4. Замени каталоги в команде grep.
