# Инструкция агенту: `.claude/rules/tdd-workflow.md`

- **Что это:** правило TDD: когда нужен, цикл красный-зелёный-рефакторинг, как писать тесты в этом проекте
- **Когда подхватывается:** всегда, в каждой сессии: у правила нет `paths:` во фронтматтере, Claude Code грузит его как часть CLAUDE.md
- **Действие при переносе:** **подстроить** — каркас общий, поменять команды, пути и примеры под проект

## Что в файле сейчас (проект «DWH-аналитик»)

- TDD для логики харнесса и MCP-сервера; не нужен для конфигов, docker, документации, карточек, переносов без
  смены поведения, ноутбуков.
- Цикл: план поведений (дано-когда-тогда со ссылками на FR) → красный тест, запуск одного теста
  (`uv run pytest tests/test_x.py::test_y -q`) → минимальный код → рефакторинг и полный `uv run pytest -q`.
- Тесты офлайн: SQLite, сценарная модель (`harness/llm/scripted.py`), демо-DWH из `tests/conftest.py`; время —
  через конфиг `prompt.now`, а не подмену часов; `pytest.mark.parametrize`; фикстуры в `conftest.py`.
- Мутационное тестирование не используется.

## Что должно быть в вашем проекте

Та же структура: где TDD обязателен и где нет; команда запуска одного теста; как в вашем проекте делаются
тесты без сети и внешних сервисов (фейки, фикстуры, тестовая БД, моки HTTP); как фиксируется время;
соглашения по параметризации и общим фикстурам.

## Шаги адаптации

1. Замени `pytest`-команды на ваш раннер (vitest/jest/go test/cargo test…) — проверь, что команда одного теста
   работает.
2. Спроси или найди, как в проекте изолируют внешние зависимости; перепиши блок «Правила» на эти механизмы.
3. Перечисли области, где TDD не нужен, по структуре вашего репозитория.
4. Правило дополняет скилл superpowers `test-driven-development`; противоречий быть не должно.
