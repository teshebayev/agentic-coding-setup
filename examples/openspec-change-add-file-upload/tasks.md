  которые нужно перенести в его proposal целиком:
  - Только сверка остатков по SKU; сверка по документам — позже. Термины — `GLOSSARY.md` (сверка остатков,
    расхождение).
  - Ключ — клиентский артикул (`sklad_dict_goods.article`), нормализация: пробелы, регистр, `123.0` → `123`.
    Модель выбирает колонки ключа и количества по заголовкам и показывает сопоставление; если вариантов
    несколько — `ask_user`. Сопоставление по штрихкоду — позже.
  - Момент сравнения — конец даты файла (остаток на начало следующего дня); даты в файле нет — `ask_user`.
    Предупреждать о ложных расхождениях из-за движений внутри дня выгрузки.
  - Наша сторона — новый инструмент MCP `stock_snapshot(client, on_date, after_article, limit≤5000)`: SQL из
    шаблона, keyset-страницы по артикулу. Инструмент сверки в харнессе сам листает страницы (до 20, то есть
    100 000 SKU), для модели это один вызов. `DWH_MAX_ROWS` не поднимаем. Скоуп — через `provider_meta`,
    чужой клиент → `access_denied`.
  - Количество — в базовых единицах номенклатуры, может быть дробным (кг). Запятая — десятичный разделитель,
    нули в конце незначимы (`100,500` = `100,5`). Исключение: в колонке есть `1,234,567` или `1,234.5` —
    запятая там разделитель тысяч. Допуск 0,001. Дубли артикула суммируются. Пустой ключ → «пропущено»,
    нечисловое количество → «не прочитано».
  - Гибрид: код выдаёт совпало / расходится / только у клиента / только у нас и xlsx всех расхождений; модель
    видит топ-20 по модулю разницы. По запросу — `sku_movements`, который научится принимать список до 50
    артикулов, период по умолчанию — 30 дней до даты сверки (правка знания, ревьюер — пользователь).
  - Правка знания: ловушка о единицах в `stock_on_date/SKILL.md` и правило в `conventions.md` — «количество в
    базовых единицах», ревьюер — пользователь.
  - Метрики: M1 ход сверки ≤ 1,5 обычного вопроса про остаток по входным токенам; M2 сверка 50 000 × 50 000
    ≤ 2 мин; M3 100 % ожидаемых групп на тестовых файлах; M4 после пилота ≥ 80 % сверок без аналитика.
