# Design: add-file-upload

## Context

Мотивация и рамки — в proposal.md. Глобальное решение «файлы по ссылке харнесса, а не через LibreChat»
записано в [ADR-0001](../../../docs/adr/0001-upload-files-via-harness-link.md). Здесь — локальные решения.

Что уже есть и на что опираемся:

- **Подписанные ссылки без ключа API.** Выгрузки (`/exports/{id}?exp&sig`) и дашборд (`/dash/…?u&exp&sig`):
  HMAC ключом `link_secret()`, исключение в `api_key_guard` (`harness/api/app.py`).
- **Объектное хранилище профиля** (`ctx.services["objects"]`: локальный каталог или MinIO) с префиксами
  ключей. Чистка по префиксу — `clean_exports()`.
- **Инъекция контекста на первом шаге хода.** `knowledge_injector` (`pre_step`, priority 96) пишет
  `context/injected` в лог. При сборке истории (`core/session.py`) событие становится блоком
  `<harness_context source=…>` в роли user. Повтор отсекается по `source` в логе.
- **Команды чата без хода.** `/справка` и `/верно` разбираются в `openai_compat.py` до `run_turn`.
- **Останов хода инструментом класса `ask`.** `ask_tools._stop_turn` (`post_tool` 5): `ask_user` пишет
  `clarification/asked` и останавливает ход с `awaiting_user`. **Любой другой** `ask`-инструмент сейчас
  уходит в ветку `escalated` — это придётся поправить.
- **Табличный артефакт** — тело `{columns, column_types, rows}`. Им пользуются `profile_artifact`,
  `export_artifact` и `render_chart`.

## Goals / Non-Goals

Цели и рамки — в proposal. На уровне дизайна дополнительно:

- без новой миграции и без новых типов событий, видимых модели (NFR-RP1);
- без новых сервисов и процессов: всё внутри процесса API харнесса.

## Decisions

### D1. Модель узнаёт о файле через `context/injected`, а не через новое событие `file/uploaded`

Контекст: FR7, NFR-RP1. На grill-сессии звучало «событие `file/uploaded`». Детальнее:

- **Решение.** Новый плагин `uploads` вешает хук `pre_step` (только первый шаг хода, priority 95 — раньше
  injector). Хук смотрит загрузки сессии в объектном хранилище и для каждой, у которой в логе ещё нет
  `context/injected` с `source = "upload:<upload_id>"`, пишет такое событие с готовым блоком о файле.
  Порядок блоков — по времени загрузки.
- **Почему не отдельное событие от роута загрузки.** Роут загрузки работает вне хода. Запись в лог вне хода
  гонится с идущим в той же сессии ходом за порядок `seq` и даёт событие, которое `core/session.py`
  должен учиться показывать. Новый тип события, видимый модели, — это правка сборки истории и риск для
  `request_hash` (NFR-RP1). `context/injected` уже показывается, уже покрыт replay и уже дедуплицируется
  по `source`.
- **Следствие.** Состояние «какие загрузки модель уже видела» живёт в логе, а не в хранилище. Replay видит
  ровно тот блок, что видела модель, даже если оригинал уже удалён чисткой.

### D2. Блок о файле: служебная рамка плюс недоверенные данные внутри

Контекст: FR7, NFR-S2, NFR-C1.

- `context/injected.content` — короткий служебный текст: «пользователь загрузил файл, id загрузки, id
  артефакта, как перечитать через `read_upload`». Ниже — сведения о файле внутри `<data source="upload">`.
  Всё, что пришло из файла (имя файла, имена листов, заголовки, ячейки), проходит `sanitize()` из
  `tools/pipeline.py` — так же, как вывод инструментов.
- Урезание до 1 500 токенов (`uploads.block_tokens`), по шагам: сначала строки превью (от
  `results.preview_rows` до 5), затем значения длиннее 60 символов, затем список колонок (первые N плюс
  «ещё K колонок»). Каждый шаг оставляет пометку. Это чистая функция над разобранной таблицей, её проверяют
  юнит-тесты на M1.
- Тот же текст возвращает `read_upload`: один формат на оба пути.

### D3. Хранение без миграции: каталог загрузки в объектном хранилище

Контекст: FR3, FR9, FR10, NFR-S3.

- Ключи: `uploads/<session_id>/<upload_id>/original<.ext>` и `uploads/<session_id>/<upload_id>/meta.json`.
  В `meta.json` — пользователь, имя файла, формат, время, результат разбора по умолчанию (лист, строка
  заголовка, число строк и пропущенных, id артефакта). `upload_id` = `upl_<16 hex>` выдаётся вместе со
  ссылкой.
- **Одноразовость ссылки** — это существование `meta.json` для этого `upload_id`. Ссылка привязана к
  `upload_id`, второй файл по ней получит отказ «ссылка использована».
- **Список загрузок сессии** для D1 — `list_objects("uploads/<session_id>/")`. Работает одинаково в обоих
  профилях.
- **Чистка** — `clean_exports` расширяется вторым префиксом `uploads/` с отдельным сроком
  `uploads.retention_days`. Команда CLI остаётся той же, отчёт показывает обе цифры.
- **Альтернатива — таблица `uploads` и миграция alembic.** Отвергнута для первой версии: таблица ради одного
  флага «использована» и списка по сессии, плюс две реализации хранилища. Если появятся поиск по загрузкам
  или квоты на пользователя — переходим на таблицу.

### D4. Разбор при загрузке, в отдельном потоке

Контекст: FR5, FR6, NFR-P1.

- Роут загрузки принимает multipart (`python-multipart` — явной зависимостью, сейчас она приходит
  транзитивно). Сначала проверяет подпись и срок ссылки, потом размер, потом сигнатуру содержимого:
  xlsx — zip, xls — OLE2, csv — декодируется как текст. Разбор идёт в `asyncio.to_thread`.
- Ошибка разбора или превышение пределов показывается пользователю на той же странице сразу, а не на
  следующем ходу. Ничего не сохраняется, ссылка остаётся годной (FR4, FR5).
- Успех: оригинал, артефакт `table` (тело `{columns, column_types, rows}`, как у `run_sql`), `meta.json`.
  `meta.json` пишется последним, поэтому сбой посередине не «съедает» ссылку.

### D5. Чтение форматов: таблицы — напрямую, текст — через markitdown

Контекст: FR6, FR11, M1.

- **xlsx** — `openpyxl` (`read_only=True, data_only=True`): быстро и без формул. **xls** — `xlrd` (приходит с
  `markitdown[xls]`). **csv** — стандартный `csv`: кодировка UTF-8 (с BOM), при ошибке — cp1251;
  разделитель из `;`, `,`, `\t` — тот, при котором больше всего из первых 50 непустых строк дают одинаковое число полей (больше 1); при равенстве — в этом порядке. `csv.Sniffer` не подошёл: падает на шапке над таблицей и при равенстве предпочитает `,`.
- **Почему не markitdown для таблиц.** markitdown отдаёт markdown-текст: типы теряются, а сверке и
  `profile_artifact` нужны числа. Обратный разбор markdown в таблицу — лишний шаг с потерями.
- **pdf, docx, pptx** — `MarkItDown().convert()` → текстовый артефакт. Формат включается только через
  `uploads.formats`. Зависимость: `markitdown[pdf,docx,pptx,xls]` без `[all]` — не тянуть распознавание
  аудио и Azure.
  **Вес `.venv`** (`du -sh`, группы dev и notebooks, 29.10.2026): до — 515M, после — 667M (+152M; больше
  всего — onnxruntime и magika для определения типа файла, lxml, pypdfium2, pdfminer). Пришло 18 пакетов,
  в том числе `xlrd` 2.0.2; `openpyxl` 3.1.5 уже был явной зависимостью.
- **Типы колонок.** Число, если все непустые значения — числа Excel или строки, которые читаются как число.
  Дата — если все даты Excel. Иначе текст. Числа вида `123.0` из Excel превращаются в `123`. Правила
  десятичной запятой для количества — не здесь, а в `add-stock-reconciliation`.
- **Строка заголовка** — первая строка, где не меньше двух непустых **текстовых** ячеек. Пустые имена
  колонок получают `col_<n>`, повторы — суффикс `_2`.

### D6. Команда `/файл` и инструмент `request_upload`

Контекст: FR1, FR2.

- Команда разбирается в `openai_compat.py` **после** `resolve_session`, рядом с `/верно`: ссылке нужна
  сессия, а для новой беседы `resolve_session` её создаёт и привязывает к `X-Conversation-Id` и ключу
  первого сообщения. В лог команда не пишется: модели знать о ней незачем. Новая беседа, начатая с
  `/файл`, получает сессию с пустым логом. Следующий вопрос найдёт её по `conv:` ключу.
- `request_upload` — локальный инструмент класса `ask`, `needs_session=True`. Плагин `uploads` в своём
  `post_tool` пишет `clarification/asked` с текстом-ссылкой в `question` и останавливает ход с
  `awaiting_user`. Новых событий нет, LibreChat уже показывает `question`.
- **Правка `ask_tools._stop_turn`.** Ветка `else → escalated` сужается до `escalate_to_analyst`. Иначе
  `request_upload` завершал бы ход как эскалацию. Сначала характеризационный тест на текущее поведение
  `ask_user` и эскалации.
- **Ссылка** — `/upload/<session_id>/<upload_id>?u=<user_id>&exp=<unix>&sig=<hmac>`. Подпись ключом
  `link_secret()` от строки `upload:<user>:<session>:<upload_id>:<exp>`. Без ключа подписи — только при
  `HARNESS_ALLOW_NO_AUTH`, как у выгрузок. В `api_key_guard` — исключение для `/upload/` с `sig`.
  Пользователь проверяется на момент загрузки: зарегистрирован, не отключён, владеет сессией.
- **Страница** — статичный HTML в `harness/api/static/upload.html` в стиле `/guide`: поле файла, кнопка,
  итог разбора (лист, колонки, строки) и фраза «вернитесь в чат и напишите вопрос».

### D7. Набор инструментов шага записывается в `step/start`

Контекст: NFR-RP1. Найдено при подключении плагина (задача 5.7): `verify_request_hashes`
(`core/replay.py`) пересобирает список инструментов по **текущему** конфигу (`ctx.tools.in_scope(mode)`),
а в `step/start` набор не записан. Два новых инструмента ломают `verify` любой сессии, записанной до
изменения, хотя записанные хэши не меняются.

- **Решение.** В `step/start` новое необязательное поле `tools` — имена инструментов, отданных модели на
  шаге. `verify` берёт из реестра только записанные имена в записанном порядке. Для шагов без поля
  (старые логи) — текущий набор минус `LEGACY_EXCLUDED_TOOLS = {"request_upload", "read_upload"}`, по
  образцу `LEGACY_MAX_OUTPUT_TOKENS`. Будущие инструменты больше не ломают старые логи, у которых поле есть.
- **Что не меняется.** `build_request` по-прежнему чистая функция, тип событий новый не появляется,
  записанные `request_hash` те же. Поле не видно модели.
- **Отвергнуто.** Принять расхождение и поправить NFR-RP1 (`verify` старых сессий только с конфигом их
  времени) — теряем проверку replay на проде. Версионировать конфиг или снимок схем инструментов —
  тяжелее, а набора имён хватает (схемы инструментов берутся из кода).

## Replay

- Сессии без загрузок: плагин ничего не пишет. `build_request` и `core/session.py` не меняются; набор
  инструментов старых шагов восстанавливается по D7, значит `request_hash` старых логов тот же.
- Сессии с загрузкой: блок о файле лежит в `context/injected` целиком. Сборка истории его только
  показывает, в хранилище не ходит. `verify` проходит и после удаления оригинала.
- `read_upload` — обычный инструмент: его результат в `tool/result`, replay его не перевыполняет.
- `request_upload` → `clarification/asked`, тот же путь, что `ask_user`.
- Проверка: `harness.cli verify` по демо-сессии, записанной до изменения, и по новой демо-сессии со
  сценарием U1. Перед завершением — субагент `replay-reviewer`.

## Risks / Trade-offs

- **[Две загрузки по одной ссылке одновременно]** Проверка `meta.json` и запись не атомарны, так что второй
  файл может проскочить. → Окно — секунды, ссылка видна только владельцу. Последствие безобидно: две
  загрузки вместо одной.
- **[Блок о файле пришёл не в тот ход]** Пользователь загрузил файл, а написал о другом. Модель всё равно
  видит блок. → Это ожидаемо: файл принадлежит беседе. Блок короткий (NFR-C1).
- **[Клиентские данные в логе]** Превью до 20 строк попадает в `context/injected`. → Как и превью `run_sql`.
  Оригинал и полный артефакт в лог не идут (NFR-S3). Срок жизни артефактов — Open Question Q1 в proposal.
- **[Транзитивные зависимости markitdown]** → Только выбранные extras. Вес после `uv sync` проверяется в
  задаче.
- **[Тяжёлый xlsx занимает поток]** → `to_thread` и пределы 10 МБ и 50 000 строк. Загрузки не параллелим
  сверх пула потоков по умолчанию.

## Migration Plan

- Миграций нет. Деплой — новая версия образа харнесса. Включение — плагин в `base.yml` и `dwh.yml`, новые
  настройки с безопасными значениями по умолчанию.
- Откат: убрать плагин из слоёв. Команда `/файл` без плагина отвечает «загрузка файлов выключена». Уже
  записанные `context/injected` в логах остаются. Шаги, записанные с плагином, хранят в `step/start.tools`
  имена `request_upload`/`read_upload` (D7), поэтому `verify` таких сессий проходит только с включённым
  плагином: без него — расхождение «нет в реестре инструментов шага».
