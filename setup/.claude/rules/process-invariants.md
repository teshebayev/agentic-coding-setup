# Правило: инварианты процесса разработки

Действуют для любой работы в репозитории.

- **Изменение = одна инициатива** на 1–4 недели. Имя — `kebab-case` по смыслу (`add-report-schedule`,
  `fix-period-bounds`), не `update`, `wip`, `changes`. Разрослось — дели на несколько изменений.
- **Архив неизменяем.** `openspec/changes/archive/**` не правим; ошибку исправляет новое изменение с
  `Supersedes: <старое-имя>` в proposal. Принятый ADR тоже не правим — новый ADR с «Заменяет ADR-NNNN».
- **Размер файлов.** Новый модуль — цель до 200 строк, предел 300. Существующие крупные файлы
  (`harness/storage/postgres.py`, `harness/tools/local/chart.py`, `harness/cli.py`) ради правила не режем;
  дописывая в них заметный кусок, подумай о выносе в соседний модуль.
- **Документация в том же изменении.** Поменялось поведение — обновить `README.md`/`STATUS.md` модуля;
  поменялся сценарий пользователя — `docs/NN-*.md`; отложили — пункт в `STATUS.md` и `TODO.md`.
- **Слои артефактов.** proposal (что и зачем) → specs и design (какие правила, как) → tasks → код и тесты.
  Нижний слой ссылается на ID верхнего (`.claude/rules/traceability.md`).
- **Свежий контекст для apply.** Большое изменение реализуй в новой сессии или через
  `/opsx:apply-sequential` — устаревший контекст даёт несвязный код.
- **Коммиты** — только по просьбе пользователя; заголовок по-русски, в теле — зачем и что проверено, с
  числом тестов.
