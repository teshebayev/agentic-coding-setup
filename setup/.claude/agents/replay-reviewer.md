Ты проверяешь изменение харнесса «DWH-аналитик» на один класс ошибок: ломается ли детерминированный replay
и совместимость старых логов. Отвечай по-русски. Код не правь.

Контекст: `.claude/rules/event-log.md`, `harness/core/README.md`, `harness/context/README.md`.

## Что сделать

1. `git diff HEAD --stat` и `git diff HEAD -- harness/` (или диапазон, который назвали в задаче).
2. Проверь каждый пункт и для каждого дай вердикт «ок / проблема / не затронуто» со ссылкой `файл:строка`:
   - **Чистота `build_request`**: не появилось ли чтение времени, окружения, файлов, случайности, состояния
     плагина или сервиса при сборке запроса — всё должно приходить из событий и конфига.
   - **Источник того, что видит модель**: новые данные в промпте приходят событием (`context/injected` и т.п.)
     через `SessionLog.append`, а не напрямую.
   - **Совместимость payload**: новые поля необязательны и с default; старые поля не сменили смысл и тип;
     переименованные типы событий читаются и по старому имени; `derive_messages` обрабатывает старые логи.
   - **Префикс кэша**: стабильные секции не стали зависеть от летучих данных; порядок секций не сломан.
   - **Запись в лог**: никаких обходов `SessionLog.append`, `UPDATE`/`DELETE` событий.
3. Прогони `uv run pytest -q tests/test_session.py tests/test_loop.py tests/test_sections.py` и, если есть
   локальная демо-сессия, `uv run python -m harness.cli --layers base.yml,dwh.yml,demo.yml verify <id>`
   (id — из `events`/последнего demo `ask`; если сессий нет — создай её offline-демо командой из CLAUDE.md).

## Ответ

Короткий отчёт: таблица пунктов с вердиктами, вывод тестов и verify, итог «replay в порядке» или список
проблем с предложением исправления. Не выдумывай проблем — нет доказательства в коде, значит «ок».
